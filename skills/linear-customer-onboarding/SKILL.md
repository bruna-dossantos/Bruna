# Linear Customer Onboarding

## What this skill does

Migrates a customer's payor coverage spreadsheet into a structured set of Linear tickets:

1. **Parent tickets** — one per `(insurance project × HCPCS code)`, lives on the DME Criteria or Infusion Criteria team, in the matched insurance project. These are the canonical "does X payor cover Y code under Z criteria" tickets.
2. **Customer tickets** — child tickets under each parent, lives in the customer's `Qual Criteria - <Customer>` project. These represent the customer's individual coverage policies.
3. **Customer Needs** — Linear's customer-feedback construct, linking each parent ticket back to the customer's record so PMs see which customers care about which criteria.

All three operations are resumable, rate-limit-aware, and gated behind human review.

## Folder structure (required)

This skill assumes two folder roots on the Desktop. If they don't exist, the first action is to create them (with the user's permission).

```
~/Desktop/Linear Master Data/          # shared across all customers, refreshed on demand
├── refresh_metadata.json
├── teams.csv                          # team name → UUID
├── dme_team_labels.csv                # label name → UUID (DME Criteria-scoped)
├── infusion_team_labels.csv           # label name → UUID (Infusion Criteria-scoped)
├── insurance_projects.csv             # project name → UUID
└── workflow_states.csv                # team → state name → UUID

~/Desktop/Customers/<CustomerName>/    # one folder per customer
├── input.csv                          # provided by user (CSV Payor, Code, Volume, [Service Line])
├── code_titles.csv                    # provided by user OR generated: Code, Title
├── customer_config.json               # team, customer UUID, customer project UUID — created on first run
├── payor_matches.csv                  # generated by match_payors.py — human-reviewable
├── parent_plan.csv                    # generated by build_parent_plan.py — human-reviewable
├── parents_created.csv                # tracker (resumable)
├── customer_tickets_created.csv       # tracker (resumable)
└── customer_needs_created.csv         # tracker (resumable)
```

## Inputs the customer folder must contain

**`input.csv`** — at minimum these columns:

| Column        | Required | Notes                                                          |
| ------------- | -------- | -------------------------------------------------------------- |
| CSV Payor     | yes      | The payor name as the customer wrote it (raw / unmatched)      |
| Code          | yes      | HCPCS code (e.g. A4351, J9035)                                 |
| Volume        | yes      | Annual volume — drives priority quartiles                      |
| Service Line  | no       | If present, used directly; otherwise inferred from code prefix |

**`code_titles.csv`** (optional) — `Code, Title` columns. If absent, the skill prompts to look up titles from a previous customer or pulls them from CMS.

## Auth

Reads Linear personal API token from `~/.linear_token` (one line, no prefix). The scripts pass it as the `Authorization` header directly.

## Walkthrough — when Bruna asks to onboard a customer

The order matters. Each step has a checkpoint where you stop and let Bruna review before proceeding.

### Step 0 — Confirm the customer

Confirm the customer name and folder. If `~/Desktop/Customers/<Name>/` doesn't exist, ask whether to create it. If `input.csv` is missing, stop and tell the user where to drop it.

### Step 1 — Ensure master data is fresh

Check `~/Desktop/Linear Master Data/refresh_metadata.json`. If it doesn't exist, or the most recent refresh is more than 7 days old, offer to refresh:

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/refresh_linear_data.py
```

This pulls every label on the DME Criteria + Infusion Criteria teams, every Insurance project, and every workflow state. It's a one-time ~30-second job.

### Step 2 — Set up customer config

If `customer_config.json` doesn't exist in the customer folder, create it interactively. Required fields:

```json
{
  "customer_name": "Comfort Medical",
  "team": "dme",
  "customer_id": "ac769570-8671-4a5a-be91-1d5c535a8e11",
  "customer_project_id": "25876cc0-d8ed-41eb-930c-ff45861d78e4",
  "customer_project_name": "Qual Criteria - Comfort Medical"
}
```

Ask Bruna for:
- The team (`dme` or `infusion`)
- The Linear Customer UUID for the customer (find via Linear MCP: `list_customers`)
- The Customer's Qual Criteria project UUID (find via Linear MCP: `list_projects` filtered by name)

Fill in `team_id`, `state_id`, `parent_estimate=2`, `customer_estimate=1` from defaults. Save and confirm.

### Step 3 — Match payors → Linear projects

Payor matching is the hardest part of this pipeline. Pure fuzzy-string matching gets it wrong constantly: it can't expand `BCBS` to `Blue Cross Blue Shield`, can't disambiguate `Anthem BCBS` (CA vs CO vs CT vs ...), can't tell that `Sunshine Health` is a Centene Florida Medicaid MCO vs an unrelated `Sunshine State Health Plan`, and can't tell Marketplace from Medicare Advantage from Medicaid MCO when names overlap. So this step is a two-phase: a script generates candidates, then **you (the LLM) make the actual matching decisions** using authoritative reference data.

**Phase A — generate candidates:**

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/match_payors.py "<CustomerName>"
```

This reads `input.csv`, dedupes CSV Payors, expands common acronyms (BCBS, UHC, KP, ABH, etc.), pulls state hints out of the payor names + any State columns, scores each payor against every Linear insurance project (combined sequence-ratio + token-Jaccard + state alignment bonus / collision penalty), and writes:

- `payor_match_candidates.csv` — top-K candidates per payor with scores and state hints
- `payor_matches.csv` — auto-confirmed rows where top score ≥ 0.95 AND margin ≥ 0.15 AND no state mismatch; everything else has `Decision=review` (or `review-state-mismatch` / `no-match`) with the matched fields blank

**Phase B — resolve `review` rows yourself:**

For every row in `payor_matches.csv` with `Decision != "auto"`:

1. Load `references/payor_taxonomy.md` for authoritative subsidiary / DBA / state-coverage data (BCBS state companies, SEC Exhibit 21 disclosures for Molina/Centene/Humana/Aetna/UHC/Cigna, Kaiser regional structure, Medicaid MCO programs by state, Medicare Advantage parent → brand mappings).
2. Apply the `insurance-mapper` skill's rubric — its 10 non-negotiable rules, LOB taxonomy (Commercial / Medicaid MCO / Medicare Advantage / Marketplace / Dual SNP / etc.), decision framework, and naming conventions.
3. Pick the right Linear insurance project from the candidate list (or from the full project list if none of the candidates fit), or mark it as truly unmatched.
4. Edit `payor_matches.csv` directly: fill `Matched Project` + `Project UUID` for resolved rows, set `Decision=manual` (or `unmatched`).

Naming convention — when you have to flag that a Linear project is missing and needs to be created, use the same naming rules the insurance-mapper skill enforces (parent payor + LOB + state where applicable, e.g. `Anthem BCBS California - Medi-Cal`, not `Anthem CA Medicaid`).

**CHECKPOINT — show the user:**
- Counts: auto-confirmed, your-resolved, unmatched
- The full list of rows you resolved manually with the reasoning (one line each: `<CSV Payor>` → `<Matched Project>` because `<short reason>`)
- Any rows you couldn't resolve and what's blocking (missing project, ambiguous LOB, etc.)
- Ask whether they want to edit `payor_matches.csv` further before proceeding

Wait for explicit go-ahead before continuing.

### Step 4 — Build the parent ticket plan

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/build_parent_plan.py "<CustomerName>"
```

This:
1. Joins `input.csv` × `payor_matches.csv` × `code_titles.csv`
2. Resolves payor + service-line label UUIDs from the team-specific labels CSV (case-insensitive name match)
3. Computes priority by volume quartile across all rows (`≥Q3 → 1`, `≥Q2 → 2`, `≥Q1 → 3`, else `4`)
4. Dedupes against existing parent tickets in Linear (queries by project + code)
5. Writes `parent_plan.csv` with one row per parent to be created

If any payor labels are missing from the team's labels CSV, the script prints them and exits. Resolve by:

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/create_team_label.py "<CustomerName>" --names "Label A" "Label B"
```

Then re-run `build_parent_plan.py`.

**CHECKPOINT — show the user:**
- Total parent tickets to create
- Breakdown by priority (Urgent/High/Normal/Low)
- Any duplicates skipped (already exist in Linear)
- Sample of 3-5 rows for sanity check

Wait for explicit go-ahead.

### Step 5 — Create parent tickets

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/create_parent_tickets.py "<CustomerName>" --sleep 1.5
```

`--sleep 1.5` keeps the rate at ~40/min, which is sustainable under Linear's 2,500/hr cap. Total time ≈ rows ÷ 40 minutes.

The script:
- Detects HTTP 400 with `RATELIMITED` → sleeps 60 min and resumes (no manual intervention needed)
- Auto-retries 429, 5xx, network errors with exponential backoff
- Writes each successful create to `parents_created.csv` immediately (resumable; just rerun if interrupted)

If Bruna wants to push faster, suggest running multiple windows in parallel (`--start`, `--limit`) — but warn that they share the hourly token budget.

### Step 6 — Create customer tickets

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/create_customer_tickets.py "<CustomerName>" --sleep 1.5
```

Identical pattern to step 5. Each ticket:
- Lives in the customer's Qual Criteria project (from `customer_config.json`)
- Has `parentId` pointing at the corresponding parent ticket (looked up from `parents_created.csv` + any pre-existing parents)
- Carries the customer's CSV Payor label (resolved from team labels) + service line label

### Step 7 — Attach Customer Needs

```bash
python3 ~/.claude/skills/linear-customer-onboarding/scripts/create_parent_customer_needs.py "<CustomerName>" --sleep 1.5
```

Loops every parent in `parents_created.csv` (plus any pre-existing parents listed in an optional `existing_parents.csv`) and calls `customerNeedCreate(customerId, issueId)`.

⚠ **Important:** Linear does NOT dedupe Customer Needs. The script's tracker prevents duplicates within its own history, but if a parent already had a Customer Need attached for this customer outside of this script, you'll create a duplicate. Ask Bruna to confirm before running on any pre-existing parents.

## Rate-limit reality check

Linear enforces **2,500 requests/hour per token**, hard. The scripts handle the cap gracefully (sleep 60 min on rate-limit, then resume), but plan accordingly:

- 1,000 parents → ~25 min at sleep 1.5
- 5,000 customer tickets → ~2.1 hours at sleep 1.5
- 10,000 customer tickets → ~4.2 hours at sleep 1.5
- 7,000 customer needs → ~2.9 hours at sleep 1.5

If you go faster (`--sleep 0.1`), you'll hit the cap, sleep an hour, repeat. Same total wall-clock; just more idle. Recommend `--sleep 1.5` and walk away.

**Don't run scripts in parallel against the same token** — they share the hourly budget. They WILL just stall each other out.

## Common mistakes & rescues

- **"Argument Validation Error: labelIds for incorrect team"** — the label UUID is from a different team. Re-resolve via team-specific labels CSV. The build_parent_plan script already does this; if you hit this error, the team labels CSV may be stale. Refresh master data.
- **`labelIds` empty / single pipe** — payor or service-line label couldn't be resolved. Run `create_team_label.py` for the missing ones.
- **Tracker CSV has stale rows from a different customer** — each customer has their OWN tracker files inside their folder. Don't share trackers across customers.
- **Customer Needs duplicated** — Linear doesn't dedupe. If you're re-running the needs script after manual cleanup, delete the corresponding rows from `customer_needs_created.csv` first OR you'll create dupes (the tracker thinks they're done, but Linear doesn't enforce).
